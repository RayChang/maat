## 2. 要解決的問題

這不是把 checklist 做成另一張勾選表，而是讓專案知道：

1. 目前有哪些支援 agent 開發的規範、內容與驗證機制。
2. 哪些缺少、哪些只是存在但沒有生效證據、哪些無法觀察。
3. 要改善某個面向，先補什麼、改哪些地方、完成後如何驗收。
4. 新專案如何從最小集合起步，後續依實際需要擴充。

報告要能供人閱讀，也能讓 agent 取得明確的改善工作與驗收依據。診斷 CLI 與診斷 Skill 保持唯讀；v1 改善 Skill 可先展示計畫與範本，經使用者明確核准後由既有 agent 修改專案。執行 scripts／測試另依授權，不能從同意修改推導為同意執行。

### 3.1 2026-11-04 的產品方向與範圍修訂

| 編號 | 使用者決定 | 邊界 |
|---|---|---|
| R-D1 | 工具提供審核標準，檢查各層是否符合，包含內容而非只有存在性 | 是本工具的符合性認定，不是 ISO 背書；方向核准不等於核准 catalog 中的 baseline 與逐題門檻 |
| R-D2 | 第一種 Skill 負責診斷 CLI 與內容審查，第二種依報告改善，搭配各層 script／skill 等範本 | 兩種職責不是新增工程層；範本是改善資源，不是唯一合規實作 |
| R-D3 | v1 改善 Skill 先展示計畫與範本，經使用者明確核准後由 agent 修改；執行 scripts／測試另依授權 | 取代 D7 的改善時程限制；不自動授權 CLI apply、模型 API、agent 啟動或完整 runner |
| R-D4 | Toolkit 本身應示範五層，區分診斷／補證據 Loop 與改善／驗收 Loop | 是待驗證的設計目標，不自稱完美或自動取得認定；機械控制依 R-D5 |
| R-D5 | 2026-11-04 核准 A：Toolkit 提供程式化狀態機、守門與紀錄，既有 Agent 執行核准動作 | 納入 v1 輕量流程核心，不納入自動 executor／完整 runner；不能阻止 host 繞過工具 |

R-D3 的核准來自使用者在選項表單中明確選擇「v1 可改善」。改善計畫、寫檔、命令執行、內容符合、任務接受是不同決定，不能以同一個完成訊號代替。

## 4. 產品邊界

### 4.1 v1

- 本機、唯讀、可重現的專案掃描；使用者提供政策或選擇目標 CLI。
- 有版本的 catalog、detector 與 CLI adapter；不是只有六個「檔案存在」檢查。
- JSON 與 Markdown 報告：證據、未知、缺口、逐層狀態與改善計畫。
- 診斷 Skill 協助說明、收集使用者回答及產生附引文的 agent 評估，不修改被診斷專案。
- 改善 Skill 依報告選用有版本的規則卡與範本，展示計畫，核准後由既有 agent 執行範圍內的修改；命令執行另依授權。
- 接受明確提供的評估與確認資料，但不自行呼叫模型 API。
- 程式化 reducer／guards 與持久流程紀錄管理兩種 Loop 的工具內轉移、核准／授權、checkpoint、停止與恢復；實際修改／執行由既有 host 負責。
- 為新專案提供最小起步計畫；也能列出既有專案採用下一個能力所欠缺的前置條件。

### 4.2 後續版本或待決

- CLI 寫檔式 init／apply 與自動命令／agent executor；改善 Skill 的計畫展示、核准修改及重新呼叫唯讀診斷已納入 v1。
- 遠端 CI／權限證據整合、報告差異比較與長期趨勢。
- MCP server、HTML 工作台與其他產品介面。
- Loop 特定的必填欄位、強制判定與可執行 hook 範本：L-D1–L-D6 已核准的方向是候選描述維度、不強制、範本待各 CLI 版本驗證後再決定。

診斷 CLI 不執行目標專案的測試、scripts、hooks、plugins 或 agent，不上傳程式碼，不自動修改政策檔。改善 Skill 由既有 agent 在明確核准的範圍修改；執行行為受另一份明確授權約束，不因掃描、範本或修改核准而自動獲准。完整 loop runner 仍屬 L-D4 的另行範圍，不由 R-D3 推導為已核准。

## 5. 核心模型

### 5.1 第 0 層與五個面向

| 識別值 | 面向 | 關注點 |
|---|---|---|
| `foundation` | 工程基礎 | 驗證指令、測試、lint、CI、開發環境與基本文件 |
| `prompt` | Prompt | 任務目標、限制、驗收條件、輸出約定 |
| `context` | Context | 知識如何提供、找到、分段載入與維護 |
| `harness` | Harness | 工具、權限、隔離、復原與可使用的驗證機制 |
| `loop` | Loop | 觸發、驗證回饋、重試、停止及從結果改進 |
| `graph` | Graph | 角色、節點、路由、交接與人的核准點 |

每題只有一個主層，必要時標記相關層，不因此重複計數。Harness 提供驗證機制，Loop 使用結果決定下一步，不能因同一個測試檔存在就讓兩者全部通過。

五層不是必須依序填滿的成熟度階梯。Prompt 與 Context 可以並行；Loop 與 Graph 都要確認適用性，不能要求每個專案都自動化或多 agent 化。

### 5.2 作法形式與證據

| 屬性 | 值與意義 |
|---|---|
| 作法形式 | 無、文字、可重用、設定；同一題可以同時具有多種形式，「無」不能與其他形式並存 |
| 證據等級 | 看到檔案、已設定未確認生效、已確認生效、無法觀察 |
| 證據來源 | `static`、`assessed_by_agent`、`attested_by_user`、`not_observable` |

形式不是通用高低排名；範本不必然比簡短指令更有效。每題自行定義目標形式與所需證據。

「已確認生效」必須有對應範圍、時間與版本的執行證據。v1 靜態掃描不能給出這種結論；使用者提供的紀錄仍標示為人工確認，不能冒充 CLI 獨立執行驗證。改善階段既有 agent 執行的結果也須保存來源與對應成果，不冒充診斷 CLI 的靜態觀察。「無法觀察」不是最低分，也不是通過。

### 5.3 單題結果與逐層狀態

單題保留以下結果；判定必須附證據邊界：

| 結果 | 定義 |
|---|---|
| `verified` | 已取得該檢查明定的證據；不延伸成 runtime 或任務成效保證 |
| `partial` | 部分要求有證據，其餘不足 |
| `missing` | 在完整且明確的搜尋範圍中，未找到要求的內容 |
| `not_applicable` | 有效的不適用條件成立，保留理由 |
| `unknown` | 無法判定，例如讀取錯誤、未支援格式、未提供適用性答案 |

逐層使用 D2 的五種狀態：

| 狀態 | 條件 |
|---|---|
| `adopted` | 適用性已確認，必要條件成立，適用的基本項達到目標 |
| `ready` | 必要條件成立，但基本項尚未完成或待確認 |
| `blocked` | 必要條件缺少或尚無足夠證據；分別列出「缺少」與「待確認」 |
| `not_applicable` | 有理由且仍有效的不適用決定 |
| `in_use_unsupported` | 有使用中的證據，但必要條件尚未成立；列為風險 |

適用性未知時先顯示待確認，不強迫給出上述某個已確定狀態。空題庫、全數未評估或全部缺乏證據，均不能產生 `adopted`。

檔案存在不等於正在使用；例如只有 subagent 定義，不能直接宣稱專案已採用 Graph。報告需區分設定訊號與使用證據。

### 5.4 能力與前置條件

- 前置條件引用有版本的能力判斷式，不使用「第 N 層達到幾分」。
- 每個能力須能追溯到 detector、證據與判定規則。
- 必要條件與建議條件分開；缺少建議條件不直接阻擋採用。
- `unknown` 不等於能力成立；agent 意見不能單獨使能力成立。
- 不適用與豁免須附理由、範圍、負責人、有效期限及證據指紋，且不能悄悄改成通過。
- catalog 不允許循環相依、未知能力引用或重複 ID。

研究中的 `commands.verify-documented`、`verifier.configured`、`recovery.available` 是候選能力。機制已採用，但 L-D2 的概念核准不等於逐題門檻核准。[Catalog 7.1](./2026-11-03-five-layer-catalog.md#71-登錄表) 已提出更名、拆分、範圍與充分證據條件；逐條 required／recommended 政策已於 2026-11-04 隨 catalog 第 7 節核准。

驗證器保護採用 [Loop 研究 12.9](./2026-11-03-loop-control-research.md#129-第四輪兩項新修正的選項) 的 P-C：不定義 `verifier.protected` 能力，也不分保護等級；報告逐項列出觀察到的保護措施、保護對象、防範的威脅、邊界、證據與未知。之後有 profile 與威脅模型時，才另行決定是否歸納成能力。

## 6. Catalog 與規則卡契約

### 6.1 每個檢查項目的九項必要資訊

下列英文欄位名是本版資料契約草案；九項資訊本身已由 D11 確認。

| 資訊 | 欄位 | 必須說清楚 |
|---|---|---|
| 唯一 ID | `id` | 穩定識別，不因顯示名稱或主層調整而重用成另一種檢查 |
| 所屬層 | `layer` | 一個主層；相關層另外記錄 |
| 適用條件 | `applicability` | 適用、不適用、未知的判斷；需要使用者回答的問題 |
| 檢查方式 | `inspection` | detector ID／版本、輸入範圍、靜態／人工／agent 方法及限制 |
| 證據要求 | `evidence_requirements` | 目標形式、所需證據、各結果條件；何時必須保持 unknown |
| 前置條件 | `prerequisites` | 必要與建議能力，如何組合；沒有時使用明確空集合 |
| 改善方法 | `remediation` | 規則卡版本、建議動作、目標位置、風險、是否需要核准 |
| 驗收方式 | `verification` | 重跑哪些 detector、預期結果、all／any 邏輯；人工項如何確認 |
| 來源 | `sources` | 原始題目／gist 段落／文件 URL 與定位、來源類型及引用用途 |

此外需有項目版本與 catalog 版本。來源類型區分研究、vendor 文件、實務建議、使用者決定、工具政策；不能把本工具的門檻說成研究結論。

「檢查方式」回答現在如何觀察；「驗收方式」回答改善後怎麼確認缺口關閉。沒有自動 detector 的題目仍可收錄，但必須提供明確的人工作答與證據要求，不以關鍵字搜尋冒充語意驗收。

### 6.2 三個概念不要混用

- **Check：** 要回答的問題與判定契約。
- **Detector：** 有版本、可重現的觀察程序；回傳事實、證據與診斷。
- **Rule card：** 改善作法與範本，可供多個 check 引用，按目標 CLI 調整。

一題可以使用多個 detector；一張規則卡也可以處理多個相關缺口。偵測規則不能藏在給 agent 的自由文字中，由 agent 自行決定是否通過。

### 6.3 來源整合與去重

整合四組來源：原始 27 題、檢視提案、gist 規則卡、工程基礎項目。不直接相加成固定題數，也不將所有項目都列為必要條件。

整合時需留下來源對照：

- 每個原始項目標示保留、改寫、合併、拆分、排除或待決。
- 保留原始 P／C／H／L／G 編號與 gist 段落定位；新 ID 不抹除來源。
- 合併多個來源時保留所有依據；拆分時交代各題責任。
- 未決項目不能列入已生效的基本項或必要條件。
- 定版前逐題檢查九項資訊、適用性、判定可行性與改善後驗收。

去重例子：

| 來源 | 整合方向 | 不可做的推論 |
|---|---|---|
| H5「寫完會自動檢查」 | Harness 的驗證機制與接線 | 有測試檔就代表自動執行 |
| L2「每一圈都有驗證步驟」 | Loop 如何使用驗證結果 | 有 CI 就代表每圈必定驗證 |
| gist「Verification Before Done」 | 上述項目的來源與改善規則卡 | 為相同要求再新增一題重複計數 |

此表說明整合方法，不預先核准 Loop 的最終通過條件。

### 6.4 gist 的使用

依 D4 可使用 gist 內容；規則卡以 `derived_from` 保存 URL、版本與段落。只將專案需要的內容放進指引、skill、範本或設定建議，不把整份 gist 塞入每次 context。

直接使用的依據為使用者確認，不是已核對到公開授權條款。公開發行前保留出處與使用依據紀錄。規則卡應採專案既有的測試與規範，不因 gist 建議而一律引入新的工具。

### 6.5 Catalog 整合的已決範圍

使用者於 2026-11-03 選定的 U-1–U-4 記錄於 [Catalog 第 3 節](./2026-11-03-five-layer-catalog.md#3-使用者決定)：

- 保留有理由的題目，摘要優先，不設固定題數或每層上限。
- 使用一份 catalog，每題列條件式 baseline；先核准選擇標準，再整份審查清單，不授權 agent 自行定案門檻。
- 驗證器保護為不評分的觀察區塊，不是檢查題、能力或採用門檻；格式草案見 catalog 6.2。
- 每個能力各自規定可接受的證據；允許有效、有依據的使用者確認，保留來源與衝突，不另加通用的獨立來源要求。

完整契約的撰寫可先完成，不等待所有政策決定；未核准的分級與通過門檻不能因文件寫齊就生效。

## 7. CLI 支援契約

第一優先的產品介面只有：

| 目標 | 支援工作 | 不自動涵蓋 |
|---|---|---|
| Claude Code CLI | 指令、skills、hooks、權限等 repo 設定面的辨識與改善計畫 | Desktop、雲端 session、Agent SDK |
| OpenAI Codex CLI | 同上，依 Codex CLI 文件與版本獨立定義 | IDE extension、App、雲端任務、SDK |
| GitHub Copilot CLI | 同上，依 Copilot CLI 文件與版本獨立定義 | VS Code／其他 IDE、coding agent、Copilot SDK |

「支援」表示工具能辨識已列入 adapter 的設定並報告限制，不是會啟動、安裝或控制該 CLI，也不表示每一項功能都可驗證。

每個 adapter 至少記錄：

- 目標產品介面、adapter 版本、已核對的 CLI 版本範圍、來源與日期。
- 實際搜尋的路徑、載入／優先順序、支援的格式與設定鍵。
- 各設定面的 `supported`／`unsupported`／`unknown` 與原因。
- runtime trust、使用者與組織設定等本機 repo 無法確認的部分。

使用者選擇目標 CLI 後，才建議補足該 CLI 專屬設定；發現某家的檔案不能自動代表使用者選擇該產品。共用檔案只讀一次也可以，但解讀結果必須分 adapter 呈現。

路徑與載入語意的候選清單見 [研究文件第 6、8 節](./2026-11-03-five-layer-tool-research.md)。實作前按 CLI 文件核對；舊的 IDE／雲端調查不能直接搬成 CLI 的規則。Copilot CLI 的查核入口包括 [官方 repository](https://github.com/github/copilot-cli) 與 [hooks 文件](https://docs.github.com/en/copilot/reference/hooks-configuration)。

## 8. 掃描、判斷與改善計畫

### 8.1 流程

```text
政策／目標 CLI + repository
  → 安全且有範圍的 discovery
  → adapter + deterministic detectors
  → 機器觀察
  → 並列使用者確認與 agent 候選評估
  → 依 catalog 判定缺口與逐層狀態
  → JSON／Markdown 報告
  → 使用者選目標
  → 依相依條件產生改善計畫，診斷到此停止
  → 改善 Skill 展示計畫與範本
  → 明確核准後，既有 agent 修改
  → 另依授權驗證；重新呼叫唯讀診斷
  → 接受、補證據、範圍內修正或停止／交人
```

掃描預設不讀 repository 外的個人設定、不追蹤越界 symlink、不執行目標程式或聯網。讀取／解析失敗要附診斷，不可轉成 missing 或成功。設定內容視為資料，不得把其中的命令當成本工具應執行的指令。

### 8.2 D8 的三類結果

每個 finding 分開保存：

1. **機器觀察：** detector 結果與原始證據。
2. **Agent 評估：** 判斷、引用位置與不確定性；只作候選。
3. **使用者確認：** 答案、範圍、證據指紋、catalog／規則版本、確認者與有效期限。

不同來源不能互相覆寫。使用者的有效確認可滿足 catalog 明定的人工要求，但不能取消機器觀察到的相反事實；矛盾要列出並保持待釐清。確認依據變更、版本不相容或到期時自動失效。

報告示例：

```text
檢查：驗證設定是否存在
機器觀察：找到測試設定；未執行測試。
Agent 評估：可能缺少登入失敗情境，附引用。
使用者確認：該情境由另一個測試專案負責，附證據與期限。
結論：設定存在；涵蓋範圍依人工證據另列，不宣稱本機已驗證通過。
```

### 8.3 報告與計畫輸出

報告至少包含 schema／catalog／adapter 版本、搜尋範圍與限制、目標 CLI、各題結果及證據來源、逐層狀態與未完成原因。

每個改善項目必須帶有：

- check ID、項目與規則卡版本、目前狀態及目標。
- 動作、目標路徑或待確認位置；不得猜測尚未知的專案指令。
- `depends_on` 與必要／建議的區分。
- 風險與是否需要人核准；hook、權限與 CI 變更預設需核准。
- 驗收 detector 與預期結果，或明確的人工作業。
- 產生計畫時的證據指紋；依據改變後不得沿用舊驗收結論。

例如「從 Harness 擴充到 Loop」應輸出還缺哪些能力、哪些基本項未達目標、哪些需要確認，以及建議順序。不得僅顯示「還差 20%」。

## 9. 政策、起步與成長

- **政策檔：** 有 schema 版本；記錄目標 CLI、適用性、目標、例外與人工確認，預期隨專案 commit。檔名與確切格式尚待定版。
- **掃描報告與趨勢：** 預設輸出 stdout、明確指定的輸出位置或 CI artifact；不自動寫回目標 repo。
- **沒有政策檔：** 仍可掃描；缺少的選擇列為待確認，不自動產生檔案。
- **新專案：** v1 產出最小核心指引、政策與 CLI 接法的起步計畫；不直接安裝全套 gist 規則。
- **成長：** 依新增驗證機制、規範分散或重複錯誤等訊號產生候選建議，附來源與成本風險，由人決定。
- **狀態保存：** 讓專案選擇既有機制；D5 的 lessons／todo 預設不等於掃描器可以自動修改 ignore 或建立檔案。

未來 `diff` 必須在版本、範圍與政策可比較時才判定退步；人工或模型意見變動不能冒充確定性 regression。這不是 v1 的隱含實作要求。

## 10. v1 改善功能的約束

R-D3 已開放 v1 改善 Skill，由既有 agent 執行核准修改；診斷 CLI 不因此成為寫檔或命令執行器。

寫檔前須展示計畫、範本與修改範圍，能預覽差異時提供差異；使用者明確核准後才修改。核准須綁定計畫、來源版本與範圍，依據改變後不得沿用。使用專案已選且涵蓋該修改的隔離／復原方式，不覆蓋無關的既有變更。命令執行另依授權，修改核准不涵蓋安裝依賴、執行測試、聯網或外部副作用。

改善後按原標準逐步驗收，未驗證與未知不當成成功。同一次修補不得同時放寬測試、lint、detector 或 CI，藉此宣稱修好。需要合法修改驗收依據時另列動作、核准與重新建立的證據，不能把舊結果移用到新標準。

具體控制者、停止／恢復與交接見[運作架構第 8–9 節](./2026-11-04-toolkit-operation-architecture.md#8-兩種-loop-與共同守門條件)。不預設固定圈數／花費／時間；使用者在取消控制表單後，於 2026-11-04 明確核准 R-D5 的 A。輕量流程核心納入 v1，不等於完整 runner 已核准。

## 11. 驗收條件

1. 相同 repository、政策與版本產生相同機器觀察；外部評估分開且可追溯。
2. 每個正式 check 都具備 D11 的九項資訊；來源對照沒有靜默遺漏，未決項不當成已生效規則。
3. 不因檔案存在、agent 聲稱完成或 CI 設定存在就宣稱 runtime enforcement。
4. 不完整掃描、讀取錯誤、未知適用性、過期確認均不能被視為通過。
5. 人與 agent 的答案分開；agent 意見不能單獨解除必要條件。
6. CLI adapter 逐產品介面、版本與設定面標示支援；不混用 IDE、SDK 或雲端語意。
7. 能列出指定面向的前置缺口、改善步驟與驗收方式，不輸出總分或通用晉級百分比。
8. 診斷 CLI／Skill 不修改目標專案、不啟動 agent、不執行專案程式、不自動聯網；改善 Skill 只修改明確核准的範圍，命令執行另依授權，失效核准不能繼續。
9. catalog、adapter 與報告的版本／引用一致，拒絕重複 ID、失效引用與循環相依。
10. 測試涵蓋正反案例、未知、不適用、部分結果、人工與機器衝突，以及設定存在但未生效的情境。

通過上述條件代表工具符合設計，不代表使用它一定提升 agent 任務成功率。
