## 2. 元件與責任

| 元件 | 輸入與責任 | 不負責的事情 |
|---|---|---|
| 審核標準 | 有版本的 checks、能力判斷式、適用性、baseline／層級條件、內容準則、證據與接受規則 | 不執行任務；不因研究或範本存在就成為已核准政策 |
| 診斷 CLI | 有範圍的本機 discovery、adapter、detectors、證據資料檢查、依標準評估、JSON／Markdown 報告與改善計畫 | 不呼叫模型、不啟動 agent、不執行專案 scripts／tests／hooks，不替專案改檔 |
| 診斷 Skill | 教既有 agent 使用 CLI、按題審查內容、提供附引文的候選、收集使用者實質回答、重評並說明結果 | 不覆寫機器觀察、不自由訂門檻、不修改被診斷專案 |
| 改善 Skill | 依報告與目標選用規則卡／範本、展示有限計畫、取得核准、交既有 agent 修改、收集驗收證據、重新診斷 | 不自封通過、不把修改核准當命令授權、不自動擴大計畫 |
| 範本資源庫 | 提供按層、題目、適用情境、產品介面與版本選擇的文字、script、skill 或設定模板 | 不把安裝當合規；不強迫替換符合標準的既有作法 |
| 流程控制核心（已核准 A） | 以程式化 reducer 與 guards 檢查狀態轉移、核准、版本、證據、停止／恢復；ledger 保存事件與狀態 | 不執行外部動作，不阻止 host 繞過工具，不證明核准身分或所有寫入都可見 |
| Host 執行環境 | 使用者既有的 Claude Code CLI、Codex CLI 或 Copilot CLI；依其權限機制執行核准修改與另經授權的驗證 | 不取代審核標準；程序停止、exit 0 或 agent 聲稱完成都不是工具的符合性結果 |

工程層、操作階段、Skill 職責、agent 程序是不同概念。同一個既有 agent 可以依次承擔兩種 Skill；不強制另開 reviewer、不同模型或另一個 session。報告須揭露已知的角色重疊及身分來源，不能偽裝為獨立審核。

## 3. 標準與符合性認定

### 3.1 標準的組成與生效

標準沿用 D11 的九項契約。內容審核準則來自每題的 `inspection.review`、`evidence_requirements` 與 `verification`，不是另用一套自由文字打分。

適用性、能力前置條件與 baseline 分開判斷。某層有必要能力成立，不代表所有適用基本項都已完成；高層不替低層通過，沒有總分、百分比或連續升級證書。

標準必須記錄版本、來源與核准狀態；變更主張、證據充分性或層級條件時須另行審查與版本更新。專案政策可以表達既有契約允許的選擇、不適用或例外，不得隱藏衝突或偷偷放寬認定要求。

**尚未定版的部分：** 41 題的分級、適用條件、能力前置條件與證據契約已於 2026-11-04 核准或核對一致，`catalog_version` 凍結為 0.1.0；工程介面尚未定版，detector 與 rule card 尚未實作，整份 catalog 仍不是可執行版本。實作前 CLI 不得發出正式符合性聲明。若執行時載入的 catalog 版本未經核准，層級欄位不給 authoritative status，附 `policy_unapproved` 診斷；不新增 `insufficient_standard` 等層級狀態，也不把未核准當成專案缺少能力。

### 3.2 認定的主張範圍

已核准規則且證據滿足時，可表述「在指定範圍內符合本工具某版本標準」。每筆認定至少能追溯：

- 被檢查的專案、工作流程／迴圈／影響範圍、目標 CLI，以及實際涵蓋與排除。
- 標準、catalog、item、adapter 與 detector 版本；材料指紋、評估時間、有效性與限制。
- 單題結果、能力判定與 D2 的逐層狀態；必要條件未知、基本項不足與不適用分開。
- `static`、`assessed_by_agent`、`attested_by_user` 的來源，以及已知的執行者、修改者、審查者與接受者。

單題仍只有 `verified`、`partial`、`missing`、`not_applicable`、`unknown`；層級仍只有 D2 的 `adopted`、`ready`、`blocked`、`not_applicable`、`in_use_unsupported`。適用性或政策未釐清時，不硬套已確定的層級狀態。

`verified` 表示該題的證據契約成立，可能只是宣告內容符合；不能與「已確認生效」混用。認定不代表 ISO 背書、外部機構認證、永久安全或任務成效保證，也不延伸到未檢查的 CLI／環境／成果版本。

報告可由專案自行執行，也可由外部觀察者執行。角色身分標示為來源所提供，無法驗證時明示；換一個 agent 或 session 不會自動形成獨立第三方認證。資料改變後保留歷史認定，但不能對新版本沿用其結論。

## 4. 內容審核，不只判斷有沒有

### 4.1 逐題審查流程

診斷 Skill 依該題契約提出下列審查材料；這是作答結構，不把每題一律加上相同內容門檻：

| 步驟 | 要回答的事 |
|---|---|
| 定位主張 | 本題在這個範圍究竟要求什麼？哪些子主張適用或未知？ |
| 定位證據 | 哪份材料、哪段文字／設定支持或反駁主張？指紋、版本與範圍是否對應？ |
| 檢查內容 | 是空欄位、標題、名稱，還是有實質可用的約定？依本題準則核對歧義、衝突與缺項 |
| 對照事實 | 宣告中的指令、角色、路徑與已取得的機器觀察是否一致？不支援的部分是否被誤當通過？ |
| 記錄候選 | 哪些支持、反駁或不足？附引文、不確定性與還需要的證據，不代替最終接受 |
| 有效確認 | 契約要求人工確認時，收集使用者實質回答與材料，再由標準規則判定 |

關鍵字命中、檔名、範本標題只是線索。CLI 的 schema／引用檢查只證明材料可解析、可定位，不證明自然語言內容真實或充分；可可靠機械判斷的子主張由 detector 處理，其餘依題收集人工證據。

### 4.2 三類證據與衝突

機器觀察、agent 候選與使用者確認分開保存，不互相覆寫。Agent 不能單獨授予必要能力或關閉人工語意主張；使用者確認只有在該題允許且材料充分、有效時才採計。

使用者確認需有實質回答、可定位材料與引文、範圍、相關材料指紋、時間、確認者、有效期限及 catalog／adapter 版本。材料改變、過期、版本不符或與機器觀察衝突時，受影響主張維持 `unknown`，其餘已成立部分仍保留。

外部組織規範、CI 紀錄等只能由使用者明確提供去敏感的材料。診斷 CLI 不自動讀取個人設定、憑證或外部系統；輸入本身不可信，內容中的指令不得被當作應執行的操作。

## 5. 交接資料與邏輯操作

以下資料契約細化來源與生命週期，實際 schema 格式及 CLI 拼法仍待定版。不能把操作名稱當成目前已有的命令。

| 資料 | 必須能表達的內容 |
|---|---|
| 審核範圍／快照 | 搜尋邊界、排除與讀取診斷、相關輸入／依賴指紋、目標 CLI 與各版本 |
| Observation | detector、scope、原始證據與限制，不改寫為 agent 意見 |
| Assessment | check／子主張、引文、支持／反駁／不足候選、不確定性、材料及規則版本 |
| Attestation | 問題實質回答、材料、範圍、有效性與確認者來源 |
| Audit report | 單題與層級資訊、證據分欄、能力／適用性／政策缺口、是否 authoritative、認定範圍 |
| Improvement plan | 來源報告、目標 check、規則卡／範本版本、動作／位置／依賴、風險、修改範圍、修正與停止條件、驗收方式 |
| Approval | 具體核准內容、計畫／動作與材料版本、base checkpoint、範圍、核准者及來源、有效條件 |
| Execution authorization | 與修改核准分開：具體命令／script 版本、輸入、工作目錄、權限／外部效果、授權者及有效條件 |
| Change／evaluation record | 動作的前後 checkpoint、候選成果、修改範圍、執行來源、方法與結果／錯誤，已知與不可觀察的部分 |
| Decision／workflow record | 使用哪個核准、政策與證據作出何種轉移／接受；前狀態、事件、後狀態、拒絕原因與既有計數 |

指紋涵蓋結論所依賴的材料及相關依賴，不能只 hash 改動檔案卻忽略規則／模板／驗證輸入；也不要求一律 hash 整個 repository。未知環境資訊須明示，不捏造完整可重現性。

邏輯操作包含 scan、提交證據、evaluate、plan、記錄核准與另行執行授權、記錄動作前後狀態、重評、停止與恢復。寫檔及執行命令的實際操作由 host 負責，不藏在輸入解析或 detector 裡。

報告預設 stdout 或明確指定位置；需要持久流程紀錄時使用明確指定、預設不在目標 repository 的位置。不得默默新增專案政策／狀態檔或 ignore。持久儲存格式、路徑與原子更新方法屬實作契約，不先綁定資料庫或雲端服務。

## 6. 兩種 Skill 的操作契約

### 6.1 診斷 Skill

先確認專案範圍與目標 CLI；沒有政策仍可掃描，但未決選擇保留待確認。呼叫唯讀 CLI，依報告載入相關題目與材料，不一次塞入全部 gist 或範本。

按照第 4 節產生附引文的候選、收集契約需要的回答，再提交明確證據供重評。沒有新材料、仍無法確認或已有有依據的結論時結束，交付報告；診斷不為了取得認證而修改專案。

報告交給改善 Skill 時包含版本、範圍、來源指紋與未知，不只提供一句「缺少第 4 層」。

### 6.2 改善 Skill

使用者選定改善目標後，依目前缺口和相依排出有限計畫。計畫先展示動作、範本或具體文字、變動範圍、風險、核准需求與驗收；未知位置／指令先確認，不猜測。

**修改前必須明確核准。** 計畫可聲明：

- 核准一份有限計畫：列明允許的動作、輸入、修改邊界、修正條件及何時重問。
- 核准每次候選修改：每個候選版本展示後各自核准。

這是計畫可表達的粒度，不新增通用預設。沒有明列修正條件的核准，不代表可以無限重試。`needs_approval: true` 仍需滿足該題的角色核准要求；false 不免除本次 v1 計畫／動作核准。

既有 agent 只執行核准動作，保留無關的既有修改。需要命令驗證時另取得具體授權；可在同一輪互動分開核准修改與執行，但不得把一般「開始改善」視為兩者都已授權。

改善後重評相關內容與必要能力。文字人工題可以按材料逐項驗收，不為了示範 Loop 強制執行 script；程式型驗收也不能用 exit 0 代替該題的充分證據。

## 7. 範本資源庫

規則卡解釋改善方法，範本提供可實例化的資源，兩者不是同一種組件。現有 43 張 rule-card 登錄不代表已有 43 個模板，也不要求每張卡或每層都必須有 script。

| 範本契約 | 要記錄的內容 |
|---|---|
| 識別與來源 | template ID／版本、所依規則卡 ID／版本、來源定位與引用用途 |
| 適用範圍 | 相關層／checks、情境、目標產品介面與 adapter／CLI 版本限制 |
| 形式與參數 | 文字、script、skill 或設定；變數、必填值、目標位置或待確認位置 |
| 可支持的主張 | 對每個引用 check 說明能協助補齊哪些內容、不能證明哪些事情 |
| 操作影響 | 擬修改路徑、執行／權限／外部效果、核准需求與復原方式 |
| 驗收與支援 | 引用本題驗收；可執行資源的已測試版本、測試依據或尚未驗證的限制 |

優先沿用專案現有作法；只有其不足時才選範本。Render 後仍有 placeholder、無對應版本或未確認輸入時不能直接套用。實例化內容及版本應包含在展示的計畫中；內容改變則重新檢查核准是否仍涵蓋。

範本被安裝不直接授予能力或 `verified`，但改善後的內容可以按該題規則與有效證據取得 `verified`。不對所有範本設「最多只能 configured」這種通用結果上限；每題主張不同。

Hook 等可執行範本沿用 L-D3：需按產品介面、版本與失敗模式核對、測試後才宣稱支援。未驗證資源可作設計說明，不視為已可可靠執行的模板。範本內的腳本不因存在於資源庫就自動獲得執行授權。

## 8. 兩種 Loop 與共同守門條件

本節是流程契約，不是新增對所有被診斷專案的 Loop 必填欄位或 baseline。依已核准的 A，由工具程式檢查其自身工作流程；B／C 未納入 v1，若未來改選，須另行修訂責任與產品邊界。

### 8.1 診斷／補證據 Loop

```text
建立審核範圍與材料快照
  → 收集機器觀察
  → 按題審查內容、收集必要確認
  → 依版本／有效性／衝突重評
  → 有新且相關材料：再次重評
  → 已有結論、無新證據、無法繼續或取消：結束本次審核
```

終點是有依據的符合／不符合／證據不足結論，或有原因的不完整審核；不是反覆掃描到全部通過。專案已知缺口可以直接產生改善計畫，不必先把它變成 unknown 或無止境問人。

評估輸入包含觀察、有效證據、適用性／政策、版本以及證據有效期狀態。相同有意義輸入產生相同機器結果；評估時間跨過證據期限是有意義變更，不因每秒時間戳不同而自動多跑一圈。

相同材料與相同主張的 agent 改寫，不算新進展。相同材料若發現新的矛盾或子主張，需具體指出差異；仍只是候選，不能單獨提升 authoritative 結果。

材料改變、失效或標準版本改變時，不沿用舊結論；保留舊快照並建立對應的新評估。沒有可靠新輸入時停止並列出待確認，而不是把 `unknown` 改成通過。

### 8.2 改善／驗收 Loop

```text
報告與改善目標
  → 有限計畫／範本 → 展示 → 明確核准
  → 檢查動作的 base checkpoint
  → 既有 agent 執行核准修改
  → 保存候選成果與修改後 checkpoint
  → 若需要執行驗證：另依授權由 host 執行，保存對應紀錄
  → 重新診斷／內容確認
  → 目標滿足：依政策接受本次改善
  → 未滿足：僅在核准的修正條件內續行
  → 新範圍、未知副作用、無進展、耗盡邊界或取消：停止／交人
```

每個動作先比對所讀／所改材料與 checkpoint。完成後將結果綁定到實際候選成果與驗收輸入；只按原先核准的動作／條件推進下一個 checkpoint。核准所允許的修改本來就會改變檔案，不能因這件事一律讓整份計畫立刻失效。

非已記錄動作造成的相關材料漂移、scope 外修改、計畫／規則／模板改變，或條件已耗盡時，必須重新展示與取得需要的核准。若選擇逐候選核准，不能拿前一個候選的核准接受下一個版本。

`evaluation result`、host 程序退出與改善接受是不同紀錄。Error、timeout、cancel、沒有執行證據或有效確認不足都不能當 pass；例外由授權者依政策明示缺漏，不偽裝為符合。

### 8.3 共同守門與恢復

| 守門條件 | 不滿足時的處理 |
|---|---|
| 政策／版本已核准且契約可解析 | 只給候選與診斷，不產生正式符合性聲明 |
| 引用、材料範圍、指紋與有效性一致 | 保留未知／衝突；不將舊證據移用到新成果 |
| 修改核准及相關角色核准涵蓋當前動作 | 不接受該動作為合法流程；重新展示或交人 |
| 執行授權涵蓋命令、輸入、權限與效果 | 不交辦未授權執行；修改核准不是替代品 |
| 動作開始的 checkpoint 匹配 | 暫停；重新確認漂移與核准，而非套用舊計畫 |
| 修正仍在原核准動作／條件內 | 否則停止，不能由 agent 自行加範圍或重置計數 |
| 有新且相關輸入，或有明確的恢復事件 | 否則不重複評估；等待有原因、有責任者 |

額度及停止邊界依每個計畫／workflow 的範圍與風險聲明，可採一次修改不重試，也可採明確有限的修正條件。沒有通用的圈數、金額、天數或必備 heartbeat；重啟不能重置該流程原應持續的紀錄。Hard limit 只在實際能強制的路徑內宣稱，未知花費只能標示估算。

恢復需核對材料、版本、核准／授權有效性與剩餘條件。若 host 動作開始後中斷，先核對當前效果，不能把缺少完成紀錄視為「沒執行」而盲目重做。不可觀察的外部效果保留不確定性並交人。

取消不自動回滾或取消外部請求。採用專案已選且涵蓋本次效果的復原／補償方法，不強制 clean tree／worktree，也不覆蓋其他人的修改。

流程違規與專案內容符合性分開。某次繞過核准的修改不能取得該次合法流程的接受紀錄；但新版本可另外做有證據的內容審核，不能因歷史違規而永久禁止認定其內容符合。

## 9. v1 機械控制方式

| 選項 | 執行責任 | 能合理宣稱的邊界 | 現況 |
|---|---|---|---|
| A：工具內建 reducer／guards／ledger；host 執行 | Toolkit 以程式管理自己的狀態、守門與紀錄；既有 agent 執行核准效果 | 拒絕工具內不合法轉移／接受；不能阻止 host 直接改檔或跳過工具 | 2026-11-04 使用者明確核准，納入 v1 |
| B：外部 host 的實際控制 | Toolkit 提供審核／資料契約，由 hooks／wrappers 等控制流程 | 只涵蓋該產品版本實際可強制的路徑；不能只靠 Skill 提示詞 | 需逐產品檢索與實機驗證，不宣稱既有研究已證明可用 |
| C：Toolkit executor／runner | Toolkit 啟動 agent／commands，管理自己的執行路徑 | 可控制自有啟動、計數與取消；仍不控制所有外部程序／效果 | 超出既有 L-D4，需明確擴張 v1 範圍及設計 |

**決策紀錄：** 2026-11-04 的控制方式表單先被取消，當時沒有把 A 的預設選取當成核准。使用者之後於 09:58（+0800）明確表示「Loop 控制方式與正式審核標準 都採用你的建議」，並列明 A 的責任範圍及「先確認 baseline 選擇標準，再整份審查 41 題」的程序。因此 A 現已核准，B／C 未納入；確認審核程序不等於 41 題門檻已通過。

在已核准的 A 中，ledger 是儲存，不是控制邏輯；reducer／guards 才是程式化控制核心。它們需檢查事件順序及狀態一致性、拒絕重複／過期的接受，並保存持續計數。持久儲存原子更新與並行修訂衝突不能只靠 agent 指示完成。

A 可防止工具在 guard 未滿足時發出正式流程接受結果，不能證明 host 每次都呼叫了它、核准身分真實、所有修改已被觀察，或外部操作未發生。未受控效果及不完整搜尋須明示。這是聲明完整性及流程守門，不是整個作業系統的強制隔離。

不因計畫可記錄核准就宣稱防偽；核准來源信任 host 與人的真實確認，驗證引用只檢查材料對應。完整 runner 也不能解決所有身分、共享工作區或遠端副作用的問題。

## 10. 一個完整案例：`prompt.task-spec`

這是 [catalog 8.10](./2026-11-03-five-layer-catalog.md#810-prompttask-spec) 的設計走查，不是實測或新增門檻。假設專案已有任務入口和空白四欄模板，沒有代表任務材料：

| 階段 | 行為與預期結果 |
|---|---|
| 初次診斷 | 四個標題不等於實質約定；本題 `detectors: []`，只有空欄位不能 `verified`，保留 `unknown` 與問題 |
| 內容審查 | Agent 指出缺少代表材料與驗收內容，附引文；候選不能單獨關閉缺口 |
| 收集確認 | 使用者提供既有代表任務：若部分內容已確認而驗收仍未定，結果可為 `partial`；沒有任何約定且有依據確認才 `missing` |
| 改善計畫 | 引用 `plan-before-act@1` 與 `definition-of-done@1` 的規則卡，補既有入口，不必新增模板系統；預覽目標、範圍與修正條件 |
| 核准與修改 | 本題 `needs_approval: false` 不免除計畫核准；核准後由既有 agent 在範圍內修改，記錄前後材料 |
| 驗收 | `rerun: []`，不是自動通過；依四項內容與一個代表用例人工核對，不要求為文字變更執行 script |
| 再評估 | 有效確認具體文字、範圍與新版材料後，依本題契約可取得 `verified`；實作完成前只能標候選，不能發正式認定 |

例如代表任務的內容可以是「修正登入失敗的訊息；只改登入畫面；不得更動驗證 API；依既有驗收規約確認指定情境的回報」。必須依實際專案補齊具體可核對的情境與依據，不能把本句當可直接通過的範本。

本題通過不代表整個 Prompt 層符合，也不證明所有未來任務都遵守。所選材料是否代表整個專案，須保留使用者確認的範圍與取樣限制，不以單一成功例子掩蓋已知反例。

若材料在核准前被其他工作改變，先停下來重檢。若本次已核准修改造成預期改變，記錄候選並重驗，而不是把它當未授權漂移。沒有新證據時重掃十次仍不能把空模板判成合格。

## 11. Toolkit 自身的五層示範

| 面向 | 示範方式 | 目前不能宣稱的事 |
|---|---|---|
| foundation | 為 parser、detectors、證據與狀態契約建立正反 fixtures／測試 | 本次沒有新增程式或測試，不能說已完成工程基礎 |
| prompt | 診斷／改善有明確目標、輸入、限制、輸出與驗收 | 文件方向不等於 Skill 已實作並被使用 |
| context | 按 check／缺口取用標準、材料、規則卡與模板，保留版本及引用 | 不靠文檔數量／模板數量證明品質 |
| harness | 唯讀診斷、host 權限、修改／執行分別核准、驗收與復原邊界 | 不把權限設定或紀錄當成不可繞過的保護 |
| loop | 診斷與改善有結果路由、停止、checkpoint 與恢復；依已核准 A 實作機械綁定 | 核准設計不等於流程已跑過或可靠，不自稱 Loop 已採用 |
| graph | 診斷、審查、核准、改善、驗收是有交接契約的邏輯節點 | 不因兩種 Skill 就宣稱有獨立多 agent 協作 |

自身審核使用同一套已核准標準與證據規則；同樣允許 `unknown` 與有依據的不適用。工具作者不能以「示範專案」自動豁免，不能在同次改善中放寬標準來取得好看的結果。

## 12. 實作驗收案例

下表是需要建立的測試，不是本次已執行的測試。內容與證據先驗收，controller 依已核准的 A 實作。

| 案例 | 應驗證的行為 |
|---|---|
| 空白模板、只有關鍵字 | 不可替代內容證據；人工題保持待確認 |
| 有效的宣告證據 | 可以滿足宣告型 check，不強制補 runtime 紀錄 |
| Agent 聲稱通過，沒有使用者材料 | 不授予能力或人工語意結論 |
| 有效人工確認與靜態觀察衝突 | 保留衝突，受影響主張 unknown |
| 草案政策／未核准層級條件 | 只給候選與診斷，不產生 authoritative 層級認定 |
| 相同輸入／候選改寫 | 不形成可提升結果的新證據；沒有進展時結束 |
| 證據到期、相關依賴或版本變更 | 受影響結果失效，依新輸入重評 |
| 修改已核准、命令未授權 | 可執行範圍內修改，不交辦未授權 command |
| 空 render、模板或計畫已變 | 不直接套用或沿用舊核准 |
| 預期修改改變 base | 正確綁定新候選與 checkpoint，不一律使計畫失效 |
| 非預期漂移／超出範圍 | 不取得本次合法流程的接受，重新展示或交人 |
| 中斷、timeout、未知外部效果 | 不當 pass／未執行，恢復先核對而不是盲目重試 |
| 無關 dirty work | 不修改、刪除或回滾；不一律要求 clean tree |
| Host 繞過工具 | 不能宣稱受到 prevention；流程違規與新快照的內容審核分開 |
| 重複／過期的狀態事件 | 不重複接受、重置紀錄或越過守門；並行衝突明示 |

文件的連結、YAML 與引用驗證只能證明文檔結構，不證明上述流程已可靠執行。
